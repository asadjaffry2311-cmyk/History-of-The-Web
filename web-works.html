Technical Explanation

How the Web Works

Every time you open a website, a precise sequence of technical steps takes place in milliseconds. This page breaks down that process — from typing a URL to seeing a page on your screen — using the core concepts of client-server architecture, DNS, TCP/IP, HTTP, HTML, and CSS.

Did you know? When you open a webpage, your browser can make over 100 separate HTTP requests — one for the HTML file, then individual requests for every image, CSS file, font, and script. According to MDN Web Docs, all of this happens in under a second on a modern connection.
The Process

What Happens When You Open a Website

  1. 1

    You type a URL

    A URL (Uniform Resource Locator) is the address of a specific resource on the Web. For example, https://example.com/page.html tells the browser three things: use the HTTPS protocol, contact the server at example.com, and retrieve the file /page.html.

  2. 2

    DNS Lookup — translating the name into an address

    Computers do not understand domain names like example.com — they only understand numerical IP addresses such as 93.184.216.34. The DNS (Domain Name System) works like the internet's phone book: it translates the human-readable domain name into the correct IP address. According to Cloudflare, this lookup usually takes just a few milliseconds because results are cached on your device, router, and internet provider.

  3. 3

    TCP Connection — establishing the channel

    Once the browser knows the server's IP address, it opens a connection using TCP/IP (Transmission Control Protocol / Internet Protocol). TCP ensures that data is delivered reliably and in the correct order. As MDN explains, the browser and server perform a "TCP handshake" — a three-step process (SYN, SYN-ACK, ACK) where both sides agree to communicate before any data is exchanged.

  4. 4

    HTTP Request — asking for the page

    The browser sends an HTTP request to the server. The most common type is a GET request — asking the server to return a specific file. According to Turing School, a typical request looks like:

    GET /index.html HTTP/1.1
    Host: example.com
    Accept: text/html

    This tells the server: "Please send me the file index.html using HTTP version 1.1, and I can accept HTML content."

  5. 5

    HTTP Response — the server replies

    The server processes the request and sends back an HTTP response. The response includes a status code — a three-digit number telling the browser whether the request succeeded. The most important codes are:

    200 OK — success, file returned
    301 Moved — page has a new URL
    404 Not Found — file doesn't exist
    500 Server Error — something went wrong

    Source: MDN HTTP Status Codes

  6. 6

    The browser renders the page

    Once the browser receives the HTML file, it reads it line by line and builds a visual page. If the HTML references a CSS file, the browser makes a separate HTTP request to fetch it. CSS tells the browser how to style the page — colours, fonts, spacing, and layout. As MDN explains, this whole process — from typing a URL to seeing a rendered page — typically takes less than one second.

Architecture

Client-Server Architecture

The Web is built on a client-server model. According to Turing School, in this model the client is always the one that initiates communication, and the server is always the one that responds. Neither side can do anything without the other.

The client is your web browser — Chrome, Firefox, Safari, or Edge. It is the software that sends requests and displays responses. The person using the browser is called the user, but the technical client is always the browser itself.

The server is a computer permanently connected to the internet, storing website files and waiting for requests. As Elementor explains, for a static site (like this one), the server simply sends pre-made HTML and CSS files. For a dynamic site (like Facebook), the server runs code and queries a database to build a unique page for each user.

Languages

HTML and CSS — Structure and Style

HTML

HyperText Markup Language

HTML is the skeleton of every web page. It uses tags — labels wrapped in angle brackets — to define what each piece of content is. According to MDN, a browser reads HTML tags and decides how to treat each element.

<header> — top section of a page </header>
<nav> — navigation menu </nav>
<section> — a thematic section </section>
<p> — a paragraph of text </p>
<a href="..."> — a hyperlink </a>
<footer> — bottom section </footer>

The <a> tag (anchor) is particularly important — it creates hyperlinks, the foundational structure of the entire Web.

CSS

Cascading Style Sheets

CSS is the visual layer of a web page. Where HTML defines what content is, CSS defines how it looks. According to MDN, CSS uses selectors to target HTML elements and properties to control their appearance.

color — text colour
font-family — typeface
margin / padding — spacing
border-radius — rounded corners
background-color — fill colour
display: flex — layout method

CSS also allows websites to respond to different screen sizes using media queries — rules that apply only when the screen is above or below a certain width, enabling responsive design.

Protocols

DNS, TCP/IP and How Data Travels

Two systems — DNS and TCP/IP — work invisibly every time you load a page. Together they handle the translation of names into addresses and the reliable transport of data across the network.

📖

DNS — The Internet's Address Book

DNS stands for Domain Name System. Every device connected to the internet has a unique IP address — a number like 142.250.185.46. DNS translates the human-readable domain name (like google.com) into that number. As Cloudflare explains, DNS was invented in 1983 by Paul Mockapetris and introduced the familiar domain extensions: .com, .org, .net, .edu.

📦

TCP/IP — Moving Data in Packets

TCP/IP is actually two protocols working together. IP (Internet Protocol) gives every device an address and routes data packets from source to destination. TCP (Transmission Control Protocol) breaks data into packets, sends them, and checks that every packet arrives correctly — resending any that are lost. According to MDN, packets can travel different routes across the internet and are reassembled in the correct order at the destination.

🔤

A Semiotic Perspective on Web Architecture

The client-server model is not just a technical architecture — it is also a semiotic structure. Every HTTP request is a sign act: the browser (sender) produces a message (the request) addressed to a server (receiver) using a shared code ( HTTP). The server interprets the message and produces a response — another sign act in the opposite direction. From a semiotic viewpoint, the Web is a continuous exchange of signs between machines, governed by protocols that function as shared codes.

HTML tags can themselves be read as signs: <h1> signals primary importance; <nav> signals navigability; <footer> signals closure. These are not arbitrary choices — they encode assumptions about how documents should be read, what counts as primary, and how users should move through information. CSS then adds a second layer of sign systems — colour, size, spacing — that carries cultural meaning independently of the text content.

Website Types

Static vs Dynamic Websites

Not all websites work the same way on the server side. According to Elementor, the key distinction is whether the server sends pre-built files or generates a unique page for each request.

Static

Static Websites

A static website consists of fixed HTML, CSS, and JavaScript files stored on the server. When a user requests a page, the server simply sends those exact files — no processing, no database. Every user who visits the same URL receives the same files.

This website is a static site, hosted on GitHub Pages. The HTML and CSS files are stored in a GitHub repository and served directly when visitors request them. Static sites are fast, secure, and free to host on GitHub Pages.

Fast Simple GitHub Pages No database
Dynamic

Dynamic Websites

A dynamic website generates a unique page for each user request. When you log into Facebook or search on Google, the server runs code (in languages like Python, PHP, or JavaScript) and queries a database to build a personalised page on the fly.

Dynamic sites can show different content to different users, handle logins, process forms, and update in real time. The trade-off is greater complexity — they require a server capable of running code, a database, and more careful security. According to MDN, most large websites today are dynamic.

Security

HTTP vs HTTPS — Security on the Web

You may have noticed that most URLs today begin with https:// rather than http://. The "S" stands for Secure — and it makes an important difference.

HTTP ⚠ Not Secure

Plain HTTP sends data as plain text across the network. Anyone positioned between your browser and the server — on the same Wi-Fi network, for example — could potentially read or alter the data being transmitted.

HTTPS ✓ Secure

HTTPS adds a layer of encryption using SSL/TLS (Secure Sockets Layer / Transport Layer Security). All data exchanged between the browser and server is encrypted — unreadable to anyone who intercepts it. According to Google's Transparency Report, over 95% of web traffic is now encrypted with HTTPS.

🔒
How to check:

Look for the padlock icon 🔒 in your browser's address bar. If it is present, the connection is encrypted with HTTPS. You should never enter passwords or personal information on a site that shows HTTP only.

Rendering

How the Browser Renders a Page — The DOM

When a browser receives an HTML file, it does not simply display the text. It builds an internal structure called the DOM (Document Object Model) — a tree of every element on the page. According to MDN, the DOM is the browser's live representation of the page, which can be inspected and modified at any time.

The browser reads the HTML from top to bottom and builds the DOM tree. Each HTML tag becomes a node in the tree. Parent elements contain child elements, just like folders contain files. For example, a <section> element might contain an <h2> and several <p> elements as its children.

Once the DOM is built, the browser applies CSS rules to calculate how each element should look — its size, colour, position, and spacing. This produces the final visual layout you see on screen. The entire process — from receiving the HTML to displaying the page — is called rendering.

The DOM is also the reason websites can update without a full page reload. JavaScript can change DOM nodes — adding, removing, or modifying elements — and the browser re-renders only the parts that changed. This is how social media feeds update instantly when you scroll.
